# EGM-003 technical design v3

Date: 2026-11-14. Status: technical design, execution manifest and active companion synchronization passed both independent reviews. Authorized as the implementation design; feature acceptance remains pending.
Policy: [ADR 0024](../adr/0024-tour-content-governance.md). Constitution v3.0.0 is unchanged.
Baseline: `f07d3d0`. [Review history](../reports/supplier-portal-egm003-design-review.md).

This document replaces the failed v1/v2 technical proposals. They are historical review evidence, not alternative active contracts. This third approach removes the speculative PostgreSQL write-context triggers and defines narrower application boundaries, explicit immutable replacement, and an executable cutover. Existing requirement IDs remain unchanged; the companion contracts must be synchronized to this document before implementation starts.

## 1. Policy and limits

The five owner-approved rules in ADR 0024 are binding. Ordinary review for exceptional corrections is the selected implementation choice, not an additional owner quote. No emergency publish path or four-eyes requirement is introduced. The correction permission has no automatic ordinary-admin grant; the existing super-admin wildcard and explicit grants apply.

The revision boundary covers canonical source text, option authored text, media, and tour presentation fields: `category_id`, `slug`, `location`, `location_slug`, `duration_minutes`, `duration_label`, `group_size_min`, `group_size_max`, `difficulty_level`, `guide_languages`, `cover_image_url`. Source locale remains immutable. Guide codes are operational facts independent of content locales; changing the displayed tour guide codes goes through the same presentation review, never translation.

Existing money, inventory, pricing-tier, availability and option commercial operations remain separate operational contracts. A revision cannot change them. Platform ownership, lifecycle and merchandising remain existing governance operations, not source corrections. Do not add departures, group pricing, new option structures or other A3/A5 workflows.

Published option additions, reactivation, retirement and reordering are refused in this slice, with localized explanation. Existing active option text can be revised; unchanged text/identity/order may round-trip in an operational price/capacity/schedule save. Draft-tour option functionality remains unchanged. This restriction is explicit, tested and recorded as remaining option-review work; it is not a claim that A3 is complete.

## 2. Reuse and actual boundaries

- Reuse `ApproveTourAction` and `TourPublicationGuardService` for first/re-publication. Keep all EGM-002 authorization, owner-first locks, lifecycle/source checks, first `published_at` semantics and atomic publication audit.
- Reuse `TourContentRules` normalization, sanitization, field bounds, source hash algorithm and owned-tour lookup. Do not feed text-only option payloads to `syncOptions`: it also changes commercial values, membership and lifecycle.
- Reuse `GovernanceAuditService`, `TourTranslationService`, `GenerateTourTranslationJob`, and the existing Gemini backend translator. Retire only the tour use of the generic field translation engine; CMS/blog retain theirs.
- Public readers, search transformers, cache hooks, booking and lifecycle paths must be inspected by symbol/call-site search before their edits. `IndexTourAction::dispatch(...)->afterCommit()` exists, but FIFO completion must not be claimed.
- No PostgreSQL GUC or trigger bypass mechanism is introduced. Enforcement is in authenticated Laravel boundaries, domain Actions/Services and the known writer inventory below. Direct operator SQL and an unpatched old application build are not supported mutation interfaces after cutover. Cutover quiescence is mandatory, not optional advice.

## 3. Storage and invariants

Add `tour_content_revisions`: `id`, `tour_id`, monotonic `revision_number`, `kind` (`legacy_baseline`, `partner_edit`, `admin_correction`, `publication`), `state` (`draft`, `proposed`, `approved`, `rejected`, `withdrawn`, `superseded`), `source_locale`, immutable full `payload`, `payload_hash`, `content_hash`, nullable `base_revision_id`, nullable `created_by`, nullable `submitted_at`, `decided_by`, `decided_at`, timestamps. Unique `(tour_id,revision_number)` and a PostgreSQL partial unique index allowing at most one `draft/proposed` row per tour. Foreign keys cascade with tour deletion; base/published pointers may only name the same tour, enforced in the locked service. Model-level guards reject mutation of snapshot/identity fields. Workflow fields may change only through the domain service.

Add `tour_revision_requests`: `id`, `tour_id`, `context` (`initial_review`, `published_review`, `correction`), nullable `base_revision_id`, nullable `revision_id`, `state` (`open`, `answered`, `approved`, `rejected`, `closed`, `superseded`), mandatory bounded `reason`, bounded `field_refs`, nullable `response_note`, nullable `response_generation_epoch`, `requested_by`, `responded_by`, `responded_at`, `decided_by`, `decided_at`, `decision_reason`, immutable `requested_content_hash`, timestamps. Keep old request reasons/fields/responses as history; never silently reuse an answered request for another revision.

Add `tours.published_revision_id`, `tours.generation_epoch` (integer default 0), `tours.content_version` (integer default 0), and `tour_translation_states.generation_epoch` (integer default 0). No separate publication epoch is required: every first/re-publication establishes a NEW approved revision ID, and revision approval additionally requires the tour currently be `published`.

`payload` contains `source` (the existing nine canonical fields), `presentation` (the fields in section 1), `options` (existing active option IDs in order, title and pickup instructions), and `media` (the faithful stored/public media projection). It contains no derivative text, currency, prices, stock, partner ID, lifecycle or provider state. Hash source text/options with the existing algorithm unchanged. Hash the entire snapshot separately for immutable replacement CAS, preserving array order.

Capture legacy baselines faithfully, including unusual media shapes or bounds: do not normalize or invent approved content. Candidate patches normalize and validate CHANGED fields using current bounds, preserve omitted legacy fields, and validate full required source title/description on submission/approval. Unchanged legacy media must not be rewritten. Media changes use the existing request shape (`url`, `alt_text`, `is_cover`) and existing cover/gallery rules. Store the normalized result before hashing. A new candidate that requires changing invalid legacy fields must obtain a partner correction; adoption never fabricates one.

A `legacy_baseline` may faithfully record an already-public row with missing or invalid source fields. Its approved state records existing public provenance, not a new approval or validation waiver; capture does not change visibility or emit `tour.publish`. Every later submission/promotion and first/re-publication still requires valid source title/description. Do not silently repair or withdraw existing public data during adoption.

## 4. Writer and lock matrix

| Entry point | Enforced behavior |
|---|---|
| Partner create / never-published draft update | Existing owned/approved-partner API and source-locale rules; live draft content is not public. Every changed canonical hash advances generation epoch under the existing content lock. |
| Partner published `PUT` | Under a fresh Tour lock, compare normalized source aliases, all governed presentation fields, media and option text against CURRENT live approved values. Any changed governed value causes one atomic 422 `content_requires_revision`; no operational sub-write is applied. Unchanged round-tripped content may accompany a legitimate operational save. Foreign IDs or structural option changes are refused. No caller can supply a governance bypass flag. |
| Partner proposal endpoints | Dedicated owned/approved-partner service; never write live content. All base/CAS/state checks happen under the Tour lock. |
| General Filament create/edit | Source and derivative writes are forbidden for every lifecycle state. Governed presentation fields cannot be administratively corrected through this form. Compare raw submitted state before relationship persistence and reject forged changes; read-only controls alone are insufficient. Remove the translation relationship repeater and old tour field-translation actions. Preserve only existing non-content operations that remain authorized and retain EGM-002 guards/transactions. If disabling canonical authoring makes admin creation unusable, hide and server-refuse creation rather than create a false functioning editor; record that intentional policy change and retain strengthened create-publication regressions. |
| Exceptional correction | Dedicated `ProposeTourCorrectionAction`, explicit `correct_tour_content`, mandatory reason/declared fields, validated canonical patch, immutable proposed revision and audit. Never writes live source or publishes. This slice supports corrections to canonical source fields; other corrections use field-specific partner requests. |
| First/re-publication | Existing `ApproveTourAction`, plus immutable approved snapshot and pointer/version establishment in its SAME transaction. No extra baseline audit duplicates `tour.publish`; include revision identity in that event. Every re-publication creates a new approved ID even for equal source text. |
| Published revision approval | Dedicated `ApproveTourRevisionAction`; reuse owner-first publication authorization/eligibility checks and required source validation. Requires exact proposed revision, current published status and exact base pointer. Writes source/presentation/media/option text, advances pointer/version and audits in ONE transaction. Does not reset `published_at` or emit a second first-publication effect. |
| Derivative generation / failure / reconciliation | Only the current source hash AND generation epoch may change derivative rows/states. All writes hold Tour first, then source and locale states. No proposed payload reaches the provider. |
| Legacy field job / itinerary adoption | Tour field jobs are refused both before provider work and immediately before any save under a fresh Tour lock. Published itinerary adoption is refused/reported; never silently writes canonical published content. Nonpublished adoption retains existing validation/epoch planning. Demo web generation remains 403. |

Publication and correction/moderation mutations lock current/proposed Partner owners in stable ID order BEFORE Tour, matching EGM-002 suspension. They then lock source, derivative states and revision/request rows in stable order. Never call the owner-locking guard from inside an already acquired Tour-first content lock. Pure partner proposal/draft/translation operations lock Tour first and never later acquire Partner row locks. Public reads take Tour shared locks and never Partner locks. Actor permissions/ownership/account eligibility are re-read, not trusted from a stale model.

All exits from `published` (admin unpublish/archive, partner archive, suspension discovery removal) make approval fail immediately through the fresh status check. On the next governance read/mutation, reconciliation marks active candidates and published-context requests superseded, with an audit. It may also be called at the known lifecycle service boundaries, but security must not depend on eager invalidation. Re-publication always advances the pointer and supersedes older candidates in its transaction. Thus archive/unpublish/re-publish cannot resurrect a candidate. Cover each existing entry point in tests.

## 5. Immutable candidate and request transitions

All candidate operations identify tour AND revision and scope ownership before validation (foreign/unknown remains 404).

| Operation | Preconditions and committed effect |
|---|---|
| Create | Tour published; caller supplies observed `base_revision_id` and it equals current pointer; no active candidate. Insert complete `draft` snapshot, new ID/number. |
| Replace | Caller supplies current active revision ID, its `observed_payload_hash`, and current base ID. Accept `draft` or `proposed`, including an active admin correction explicitly being replaced. Merge patch against THAT stored candidate, insert a NEW immutable `draft` row, mark old row `superseded`, return NEW ID/number. Never mutate payload under a reviewed ID. Linked answered/correction requests become `superseded`; unlinked open requests remain open. |
| Submit | Owned current `draft`, current base/published tour, valid required source. Set `proposed`, stamp submission, audit once. |
| Approve | Exact `proposed` ID shown in review, published Tour, current base and valid payload/owner/permissions. Promote atomically. Mark linked answered requests approved; other open requests for the same base close with an explicit approval decision reason, without claiming a partner response. |
| Reject | Exact current `proposed`, admin `manage_tours`, mandatory reason. Set `rejected`; linked requests rejected. New work requires an explicit new candidate/request. |
| Withdraw | Owner withdraws current partner-authored draft/proposed. Set `withdrawn`; linked requests superseded. Admin corrections can instead be rejected by a reviewer or explicitly replaced by the owning partner. |
| Stale base or nonpublished Tour | Commit `superseded` plus request effects/audit in the transaction; return a conflict RESULT. Throw/render 409 only AFTER that transaction commits. Do not throw inside then falsely claim supersession persisted. |
| Replay | Superseded -> 409 `REVISION_SUPERSEDED`; other terminal states -> 409 `REVISION_TERMINAL`. No duplicate audit/publication/derivative effects. |

Change requests require reason trimmed nonempty/max2000 and 1–30 allowed, resolvable field references. References use canonical field names, presentation field names and stable option IDs/media positions from the captured context. A correction's actual changed paths must be a subset of declared fields; reject undeclared changes, derivative paths and no-effect corrections. No arbitrary minimum of ten characters.

Wire references are objects `{"path":"source.title","note":"optional explanation"}`; only `path` and optional plain-text `note` (max500) are allowed. Paths use stored snapshot tiers: `source.*`, `presentation.*`, `options.{stable_id}.title` / `pickup_instructions`, and `media.{position}.alt_text`. The canonical schema fields are always defined, even when their legacy value is null.

Published requests capture the approved base. Partner response links ONLY the current owned submitted candidate with that base. It stores a bounded note and sets `answered`; another tour, rejected/withdrawn/superseded candidate, or old base is refused. A later replacement preserves the old request as superseded history; the reviewer can issue a new request if needed.

Initial-review requests are also supported on draft/pending/rejected never-public tours: capture the source hash/epoch and fields. A pending-review tour becomes rejected with the mandatory reason through the existing rejection lifecycle; a draft or already rejected tour keeps that state. Require the partner response's observed epoch to equal the current owned source epoch. Canonical schema fields can be referenced even when their value is missing; option/media references must identify existing entries. No published revision ID is invented. Existing draft editing/submission/first-approval source validation remains authoritative. A later initial approval closes its requests with a recorded reviewer decision. This does not claim immutable public content exists before first publication.

Every successful correction, request, response, submission, supersession, rejection and revision approval records actor, tour/revision IDs, reason/fields as applicable, before/after state and time through `GovernanceAuditService` in the mutation transaction. Do not duplicate full content in audit rows. Audit failure rolls back the governed mutation. Rejected unauthorized calls create no successful correction/approval audit.

## 6. Exact additive partner API

Use existing auth, partner middleware, ownership lookup, throttle and envelope/error conventions. All GET payloads below are owner-only. No public or admin REST approval endpoint is added.

Revision source PATCH input reuses the existing authored `translations.{fixed_source_locale}` / canonical shorthand normalization; the stored full snapshot calls that tier `source`. Clients map the owned snapshot back into the write shape, rather than round-tripping platform metadata or attempting to select another locale. This mapping is explicit in the Spec 019 contract and frontend request types.

- `GET tours/{id}`: return `content_governance` for every owned tour, including current generation epoch, nullable approved ID, nullable active candidate metadata and request summaries. For published legacy tours, lazily capture a baseline under the Tour lock BEFORE returning it. Never return null capability on a published tour that is now protected. Never-public tours expose a null approved ID and their real epoch so initial-review responses do not need an invented revision.
- `GET tours/{id}/revisions/{revisionId}`: full immutable payload, payload hash, kind/state, base ID, timestamps, reason/fields and normalized diff versus base. This restores a candidate after refresh and lets the admin see the exact compared snapshot. Only the payload hash is an exposed replacement token; canonical source/content hashes and provider/translation diagnostics stay internal, preserving the existing partner projection boundary.
- `GET tours/{id}/revisions`, `GET tours/{id}/revision-requests`: bounded paginated histories, scoped to this tour.
- `POST tours/{id}/revisions`: observed base ID plus bounded source/presentation/options/media PATCH; 201 new draft with complete payload metadata. Active-candidate conflict is 409 and identifies the conflicting revision.
- `PUT tours/{id}/revisions/{revisionId}`: observed base ID + observed payload hash + patch; 200 with NEW replacement ID and full payload metadata; old ID superseded. The endpoint name does not mean mutable snapshot storage.
- `POST .../revisions/{revisionId}/submit`, `POST .../revisions/{revisionId}/withdraw`: 200 state response or documented 409/422/404.
- `POST tours/{id}/revision-requests/{requestId}/respond`: submitted revision ID for published context, or observed generation epoch for initial context, plus bounded note; 200 answered request; mismatching tour/ownership 404, stale context/state 409, invalid refs/link 422.

Error codes: `content_requires_revision`, `option_structure_change_not_supported`, `REVISION_CONFLICT`, `REVISION_ALREADY_OPEN`, `REVISION_SUPERSEDED`, `REVISION_TERMINAL`, `REVISION_CONTENT_INVALID`, `REQUEST_NOT_OPEN`, `unknown_field_reference`, `undeclared_field_change`. Report exact offending input paths. Never silently drop mixed dirty commercial/source fields.

## 7. Translation identity and recovery

The canonical source identity is existing normalized source hash plus monotonically increasing `generation_epoch`. Advance epoch when the source hash changes, including active option source text. Advance it also for an explicit authorized force-regeneration, even with equal text, to fence older work. Media/presentation-only approval does not advance this epoch; in-flight work for identical canonical content remains valid. This distinguishes canonical generation identity from the approved full snapshot identity.

Plan/dispatch tuples include epoch. New jobs carry it; the constructor tolerates missing legacy epoch as null for queue deserialization but NULL never equals current integer epoch. An old legacy job performs no success/failure write. Current jobs preflight AND recheck after provider I/O under the Tour lock: locale derivative, current hash, tour epoch, desired-state hash/epoch, and not already current. Failure callbacks use the SAME identity fence and cannot turn current ready work into failed. Completion persists derivative source/options and ready state atomically, bumps content version and schedules projections after commit. Never translate proposed content or guide codes.

Desired-state rules are explicit: matching hash+epoch and ready+real row -> preserve; matching pending/stale -> allow duplicate requeue for recovery; failed -> retry by reconciliation; mismatching epoch/hash -> overwrite desired identity, mark stored derivative stale or missing derivative pending, and enqueue current work. A matching ready state without a row is unfinished. Currency requires desired and translated hash/epoch match the current tour; if using one state epoch, advancing desired identity MUST clear translated currency before marking pending/stale. Keep existing successful derivatives for source fallback/history; never label them current by hash alone after A-B-A. Reconciliation replaces orphan epoch-less/old pending jobs rather than preserving an unrecoverable pending state.

Keep existing bounded retry/backoff/error sanitization and Gemini configuration. Missing, pending, stale or failed derivatives do not block eligible review approval. Public fallback is the NEW approved source with localized source-language notice. No live provider smoke is claimed by fake-provider tests.

## 8. Public reads, cache and index coherence

Use a single Tour-shared-lock read boundary in a domain service/Action, before eager-loading and building governed detail/card/index projections. Approval and source/derivative writes serialize on Tour, so one payload cannot straddle promotion. Batch-lock sorted Tour IDs for card collections and reload the relations used by the transformer; do not introduce a per-card N+1 query loop. A booking that copies option text/locale also observes one coherent approved snapshot using the existing Tour/option locks; it never reads proposed payloads.

For detail requests, under the shared lock validate fresh lifecycle and owner/public eligibility BEFORE any cache hit, read `content_version`, then get/build `tour.{slug}.{locale}.{content_version}`. Cache fill completes before releasing that lock. Increment content_version in the SAME transaction on approval, first/re-publication and every public derivative state/content transition, including failure/reconciliation. This fences old fills against new canonical promotions. SEO derives from the same returned displayed content/fallback; no separate proposed SEO source exists.

Preserve EVERY existing invalidation event rather than abandoning its key. Introduce one cache invalidator used by existing Tour, translation/state, option/option-translation/media, pricing/availability and lifecycle hooks that currently invalidate detail. It evicts BOTH the legacy key and the current versioned key after commit, for each locale and old/new slug when changed. All current callers must be enumerated by code search and tested. Operational changes that do not bump content_version still evict the current key; do not retain a newly stale 900-second cache. This preserves existing operational invalidation semantics, without claiming new linearizable inventory caching.

Explicit after-commit indexing reloads coherent CURRENT approved rows; no candidate is materialized/indexed. Queue completion is not FIFO. Search selection/ranking and existing list/homepage caches retain their documented eventual consistency; they may briefly show a PREVIOUSLY approved projection, never a proposed one. Hydrated search cards must not mix approved revisions, and public detail always revalidates current status. Do not claim simultaneous distributed-index convergence. Record actual cache invalidation targets and remaining index lag in the implementation report.

## 9. UI and mixed-save behavior

Partner edit loads full active candidate when present, otherwise approved content. Display a persistent localized notice that current public content remains unchanged. Save a published content draft, submit it, view field-specific requests and respond; show proposed/rejected/superseded/approved states. A replacement switches to the returned NEW ID. Conflict UI retains entered values, offers reload/compare/reapply and never silently replaces a newer candidate.

Choose separate saves for mixed dirty fields: if governed content AND commercial fields changed, make NO request, retain all values and show localized instructions to save operational changes separately. Provide explicit content-draft save and operational-only save controls using their respective payload builders; each sends only its own allowed fields. After either succeeds, refresh that saved baseline while retaining the other dirty fields. If either fails, keep dirty values and announce the error. Tests must demonstrate source-text plus option-price changes are neither lost nor partly applied.

Admin review shows the exact proposed revision ID, full source/presentation/media/option-text diff, base and request reasons BEFORE offering approve/reject. Capture that ID/hash in action state, not 'latest candidate' at callback time. Exceptional correction fields are a separate permission-gated dialog and domain Action; derivatives are read-only. Existing first-publication moderation still uses EGM-002. Partner copy ships EN/ES/IT, uses semantic tokens/shared components and keyboard focus/error announcements.

## 10. Cutover and rollback

This is one coordinated activation, not a release where snapshot pointers coexist with unrestricted writers. Do not deploy or migrate a real environment in this task.

Production runbook prerequisite: enter maintenance for partner/admin writes and stop queue producers/schedulers; gracefully stop OLD workers and wait for their current jobs/provider calls to finish (bounded by configured timeout, verify process exit). The queue is NOT claimed to empty while workers are stopped. Deploy the COMPLETE new application/guards/readers, apply additive schema, capture published baselines in bounded idempotent Tour-locked batches (faithful payload, pointer-if-null CAS), and reconcile current derivative states/epoch-aware jobs. Queued/delayed old jobs may remain: new workers safely no-op their null epoch and reconciliation queues replacements. Restart ONLY new workers, verify health and then resume producers/traffic. No old PHP worker may survive activation. Exercise this sequence with disposable fixtures; production execution requires separate authorization.

Lazy baseline is also mandatory on first owned published GET, proposal/correction/request creation and review use, so a legacy row missed by a batch still works load→propose→submit. Baseline capture and concurrent source/promotion use the same lock and cannot overwrite an established pointer. First/re-publication seals current live draft as a new approved revision in the publication transaction and reconciles old candidates. Invalid legacy source is not silently repaired or newly approved.

After activation, supported rollback is to a compatible build retaining all governance guards/readers, with proposal/correction/approval writes disabled if necessary. Do NOT run the pre-policy backend against adopted data; it lacks enforcement. An older frontend may fail to save published content and must show a recoverable error; it cannot bypass the backend. Do not destructively drop accepted snapshots or columns; migration down is tested only on a disposable pre-adoption schema. Roll forward for schema/data corrections. Stored booking snapshots are never rewritten by backfill, proposal or promotion.

## 11. Acceptance and implementation gates

Keep existing FR/SC IDs; existing v1/v2 technical AC labels may be mapped to these checks, but no historical pass is rewritten. Before code, synchronize Specs 018–020, Supplier plan and the dated Goldfish decision with this reviewed design.

1. Reproduce forged general Filament source and derivative writes before fix. After fix, all EN/ES/IT source/derivative attempts leave rows unchanged; correct source fields cannot be modified via unrelated presentation/cover aliases.
2. Direct partner/service published writes fail atomically for every governed alias; operational-only unchanged-content round-trip still works. Structural published option changes fail closed without damaging commerce.
3. Legacy load→proposal→reload→replacement→submit→field request→response→review works with mandatory base/hash, full owned payload and cross-supplier 404.
4. Proposal/under-review/correction content never reaches detail, card/search/index, SEO, media or Gemini. Approval promotes all governed fields atomically; old/new option commercial facts are preserved. Confirmed booking snapshots remain unchanged, and a concurrent new booking sees one approved option text/locale.
5. Real PostgreSQL process barriers cover replacement-versus-approval, double approval, superseded-versus-current, approval-versus-suspension, archive/unpublish/re-publish, backfill-versus-first-use and public read/cache fill versus promotion. Observe actual database blocking; sequential hash assertions alone are insufficient.
6. A-B-A success AND failure callbacks, legacy null-epoch jobs, first-publication crossing, same-hash presentation approval, lost queue pushes and mismatch reconciliation are tested. Existing translation concurrency/fallback tests remain green.
7. Correction permission/revocation, reason/declared fields, ordinary review and audit rollback are verified with real Actions/Livewire. No implicit publication or self-appointed emergency mode.
8. Versioned cache operational invalidation, unpublish/archive/owner eligibility on hits, failed→pending→ready state changes and after-commit final-state indexing are tested.
9. EN/ES/IT partner UI, mixed dirty saves, reload/conflicts, keyboard/error focus, empty/loading/error/permission states; browser acceptance at 390/768/1024/1440 with Axe. Real admin→partner→public journey, not a mocked replacement wizard.
10. Existing EGM-002 and EGM-004 semantic regressions stay covered. Old tests that positively allowed direct admin source correction must be strengthened to the approved policy, never deleted to hide failures.

Implementation slices: (S1) schema/models/baseline and PG constraints; (S2) immutable service, writer restrictions and first-publication integration; (S3) requests/corrections/review Livewire; (S4) epoch-aware generation/legacy retirement/reconciliation; (S5) coherent projections/cache/booking compatibility; (S6) partner API/editor/localization and browser acceptance. Each slice adds failing regressions first and runs its focused gates. No unrelated feature work.
