# Implementation Plan: Partner Dashboard — Tour Creation, Booking Management & Partner Profile

**Branch**: `012-partner-dashboard` | **Date**: 2026-06-03 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/012-partner-dashboard/spec.md`

## Summary

Build the Partner Dashboard — a dedicated management interface for marketplace partners. Includes: analytics overview dashboard, multi-step tour creation wizard with draft save, booking management with filters and status updates, review management with response capability, partner profile/settings/payout management, analytics page with date range and tour filters, and real-time notifications. All pages are partner-auth-guarded, responsive, localized (EN/ES/IT), and accessible (WCAG 2.1 AA).

## Technical Context

**Language/Version**: TypeScript 5.x, Next.js 16 (App Router)
**Primary Dependencies**: React 19, Tailwind CSS, shadcn/ui, Zustand (wizard state), TanStack Query (data fetching), next-intl (i18n)
**Backend**: Laravel 12 (PHP 8.3) with Partner domain (`backend/app/Domains/Partner/`)
**Database**: PostgreSQL + Redis (cache/queue/session)
**Storage**: Cloudflare R2 via presigned URLs for tour media uploads
**Real-time**: Laravel Echo/Reverb WebSocket on `private-partner.{partner_id}` channel, 60s polling fallback
**Auth**: Laravel Sanctum + PartnerRoleMiddleware (sets `partner_id` on request, returns 404 for cross-partner access)
**Security**: Cross-partner access returns HTTP 404 (not 403) to prevent information leakage
**Encryption**: Payout fields (`payout_account_number`, `payout_iban`, `payout_swift_bic`) encrypted at rest via Laravel Crypt, masked on read
**Validation**: Custom `ValidIban` rule implementing MOD 97 checksum algorithm
**Testing**: Pest PHP (backend contract tests), Playwright (frontend E2E)
**Target Platform**: Web (Chrome, Safari, Firefox, Edge), responsive mobile-first
**Performance Goals**: Dashboard render < 2s; draft save < 1s; Lighthouse Performance ≥ 90
**Constraints**: WCAG 2.1 AA; mobile breakpoints 390px / 780px / 1280px; 3 locales (EN, ES, IT)
**Scale/Scope**: 6 partner routes, ~25 components, 7 controllers, 6 services, 7 broadcast events

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Evaluation | Status |
|---|---|---|
| I. Marketplace-First | All UI surfaces serve marketplace partners managing their tour offerings. | PASS |
| II. Tours-Only Discipline | All new pages (dashboard, tours, bookings, reviews, analytics, profile) are tour-centric. | PASS |
| III. Direct Booking Only | No inquiry/request-based flows; booking management is lifecycle management of existing bookings. | PASS |
| IV. Admin-Governed Publishing | Tour creation → pending_review → admin approval flow enforced. | PASS |
| V. Platform-Controlled Commerce | No direct payment handling; payout info is stored, actual payouts are platform-managed. | PASS |
| VI. Completed-Booking Review Integrity | Review responses are partner-initiated only for completed-booking reviews. | PASS |
| API-First | All data fetched from Laravel APIs via authenticated partner endpoints. | PASS |
| SEO-First | Partner dashboard pages are behind auth; SEO metadata for discoverability is not required. | N/A |
| Security-First | PartnerRoleMiddleware sets partner_id (returns 404 for cross-partner), IBAN validation, signed URL uploads, payout field encryption. | PASS |
| Thin Controllers / No Direct DB Access | Backend controllers delegate to services (TourService, BookingService, ReviewService, AnalyticsService, ProfileService, NotificationService). | PASS |

**Structure Decision**: Partner pages use a dedicated route group `(partner)` with its own layout (sidebar + header). Backend Partner domain uses DDD structure with thin controllers delegating to services. Frontend uses Zustand for wizard state (persisted to localStorage), TanStack Query for server state, and the existing API client. Real-time updates via WebSocket with polling fallback.
